# Design doc sections

Propose the section list to the user before writing. Core sections always appear. Add only the domain sections this project needs.

## Core sections

1. **Problem and goal:** the "How might we" line and what success looks like.
2. **Users and context.**
3. **Goals and non-goals.** Non-goals come from the don't-want list.
4. **Scope:** first version, later, not planned.
5. **Key decisions:** each with its decision number, a one-line reason and the main alternative that was rejected.
6. **Domain sections** (below).
7. **Risks and how they are handled.**
8. **Open questions and assumptions to validate.**

## Domain sections

- **Software:** architecture overview, data model, interfaces or API, screens and flows, tech stack, security and privacy, deployment, testing approach.
- **Game:** core loop, mechanics and rules, player experience and tone, progression, content list, art and audio direction, platform and controls.
- **Physical build:** parts and materials, dimensions, tools and build steps, budget, safety.
- **Other:** propose sections that answer what the builder needs to know, and explain each in one line.

## Level of detail

Follow the Builder answer from the interview.

- **AI coding agent:** explicit names, data shapes, file or module boundaries, and acceptance criteria per feature. It will not ask, it will guess.
- **The user themselves:** decisions and reasons, less spelled-out detail.
- **A team:** enough that two people reading it build the same thing.
